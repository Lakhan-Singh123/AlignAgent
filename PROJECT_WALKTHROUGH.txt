--------------------------------------------------------------------------------
WHAT DOES THIS PROJECT DO?
--------------------------------------------------------------------------------

You upload your resume (PDF) and paste a job / internship description.
AlignAgent reads both, compares them, and gives you a complete career toolkit:

  - Readiness score (0–100%) showing how well you fit the role
  - Skills you already have vs. skills you are missing
  - Week-by-week learning plan to close the gaps
  - Free resources (courses, docs, videos) for each missing skill
  - Likely interview questions for that role
  - Specific suggestions to improve your resume
  - ATS compatibility check (will your resume pass the bots?)
  - AI-written cover letter tailored to the job
  - AI-rewritten resume PDF optimised for that specific JD
  - Side-by-side comparison of multiple jobs
  - Skill progress tracker in the sidebar

It runs on Groq's free API (llama-3.3-70b-versatile) and is deployed live at:
  https://alignagent-yboyjjcrws3vkuc3yujiub.streamlit.app


--------------------------------------------------------------------------------
THE BIG PICTURE — TWO MODES
--------------------------------------------------------------------------------

When you click "Analyse my fit", you choose between two modes:

  QUICK MODE (~30-60 seconds)
  ----------------------------
  Resume text + JD text → directly fed to the LLM → LLM returns the report.
  Simple. Fast. No vector database involved.

  DEEP MODE (~2-3 minutes)
  -------------------------
  Resume + JD → stored in a FAISS vector database → LLM generates search
  queries → retrieves relevant chunks → grades them for relevance →
  web searches if needed → generates report → checks its own report
  for hallucinations → retries if needed → saves report → enriches resources.
  More thorough. Uses an 8-step agentic LangGraph pipeline.

Think of it like this:
  Quick mode = asking a friend to read both documents and give instant feedback.
  Deep mode  = hiring a researcher who organizes the documents, searches
               through them methodically, fact-checks their own work, and
               then gives you a thorough verified report.

FILE 1: app.py  (the front door)
--------------------------------------------------------------------------------

This is the only file you need to run:
  streamlit run app.py

It imports everything else and wires it together. Nothing AI or ML happens
directly inside app.py — it just calls functions from other files and displays
the results.

--------------------------------------------------------------------------------
FILE 2: analyzer.py  (all the LLM calls)
--------------------------------------------------------------------------------

This file talks to Groq (the AI API). Every function in here takes text
in and returns text or a dictionary out.

KEY FUNCTIONS:

  _llm()
    Creates and returns a ChatGroq object using the GROQ_API_KEY from .env.
    Model: llama-3.3-70b-versatile. Temperature: 0.2 (focused, not creative).
    Called fresh each time so there is no shared state between calls.

  extract_text_from_pdf(pdf_file)
    Uses PyPDF's PdfReader to extract all text from a PDF file object.
    Returns one big string of all the resume text.
    IMPORTANT: After calling this, the file stream position is at the end.
    If you need to read the file again, call pdf_file.seek(0) first.
    (This was a real bug we fixed — deep mode was getting empty bytes.)

  get_ai_analysis(resume_text, job_description)
    The quick mode master function. Calls the LLM in 3 steps:
      Step 1: _get_skills_and_score() — matched skills, missing skills, score
      Step 2: _get_plan_and_resources() — week-by-week plan, resource links
      Step 3: get_interview_questions() + get_resume_suggestions()
    Returns one big dictionary with all results.
    Has a _local_fallback() that uses regex if the LLM fails.

  get_interview_questions(missing_skills, matched_skills, jd)
    Asks the LLM for 6 realistic interview questions.
    3 about skills the candidate lacks, 3 about skills they have.

  get_resume_suggestions(resume_text, jd, missing_skills)
    Returns 5 specific, actionable suggestions to improve the resume.

  check_ats_score(resume_text, job_description)
    ATS (Applicant Tracking System) compatibility check.
    TWO-STEP process:
      1. _ats_local(): Fast regex checks — no API call needed.
         Checks for: email/phone, LinkedIn, Education/Experience/Skills sections,
         quantified achievements (numbers, %), action verbs, word count.
         Returns ats_score, keyword_score, section_score, found/missing keywords.
      2. LLM step: generates 5 specific improvement suggestions.
    The local checks are instant. LLM suggestions take ~5 seconds.

  generate_cover_letter(resume_text, job_description, matched_skills)
    Asks the LLM to write a 3-4 paragraph professional cover letter.
    Tailored to the specific role. Avoids generic phrases.
    Has a plain-text fallback if the LLM call fails.

  generate_tailored_resume(resume_text, job_description, matched_skills, missing_skills)
    Asks the LLM to rewrite the resume as structured JSON, optimised for the JD.
    Rewrites bullets with stronger action verbs and quantified impact.
    Tailors the professional summary to the role.
    Reorders skills so most JD-relevant appear first.
    Returns a dictionary with: name, email, phone, linkedin, github, summary,
    experience (with rewritten bullets), skills, education, projects.
    IMPORTANT: never invents companies or degrees — only rewrites existing content.

  scrape_jd_from_url(url)
    Fetches a job posting page and extracts its text using BeautifulSoup.
    Protected by SSRF guard in app.py that blocks localhost/internal IPs.

  _extract_json(text) and _repair_json(text)
    Helper utilities that parse JSON from LLM responses even when the model
    wraps it in markdown fences or truncates it mid-output.


--------------------------------------------------------------------------------
FILE 3: ingestion.py  (building the vector database)
--------------------------------------------------------------------------------

Used ONLY by deep mode. Quick mode never touches this file.

WHAT IS A VECTOR DATABASE?
  Normal search: looks for exact words.
  Vector search: converts text to numbers (vectors), then finds text
  that is SIMILAR in meaning, even if it uses different words.
  Example: "Python programming" and "coding in Python" would both match
  a query about "Python development".

CLASS: MultiTenantIngestionPipeline

  "Multi-tenant" means each analysis session gets its own isolated storage.
  The workspace_id (a random UUID) keeps one user's resume separate from another.

  KEY PARAMETERS:
    workspace_id         Unique ID for this session (e.g. "session_a1b2c3_candidate")
    base_workspace_dir   Root folder ("workspaces/")
    embedding_model      FastEmbed model: "BAAI/bge-small-en-v1.5" (384 dimensions)

  HOW IT STORES DOCUMENTS (Parent-Child Chunking):
    Every document is split TWICE:
      Parent chunks: 1200 characters with 200-char overlap
      Child chunks:  300 characters with 50-char overlap

    Child chunks → embedded into vectors → stored in FAISS (for fast search)
    Parent chunks → stored in LocalFileStore (as plain files on disk)

    When you search, you find child chunks (small, precise), then return their
    parent chunks (bigger, more context). This gives precise matching but
    rich context in the response.

  METHODS:
    load_documents(file_path)   Loads PDF/DOCX/TXT into LangChain Documents.
    ingest(documents)           Splits, embeds, and saves to FAISS + LocalFileStore.
    get_retriever()             Returns a ParentDocumentRetriever ready to search.

  WHAT IS FASTEMBED?
    FastEmbed converts text to 384-dimensional number vectors using the
    BAAI/bge-small-en-v1.5 model. It is lightweight (uses ONNX, no PyTorch/GPU
    needed) and downloads the model automatically on first use (~25MB).
    This replaced HuggingFace sentence-transformers which required heavy
    PyTorch/torchvision dependencies that caused deployment issues.


--------------------------------------------------------------------------------
FILE 4: graph.py  (the 8-node AI agent)
--------------------------------------------------------------------------------

This is the brain of deep mode. Uses LangGraph to build a directed graph
where each node is a step and the AI can loop back if needed.

WHAT IS LANGGRAPH?
  LangGraph is a library for building AI pipelines that can branch and loop.
  Think of it like a flowchart where each box is an AI step.

THE AGENT STATE (AgentState):
  A TypedDict (Python typed dictionary) that travels through all 8 nodes.
  Every node reads from it and writes back to it. Fields:
    candidate_id / internship_id     Workspace IDs for retrieval
    candidate_queries / internship_queries   Search queries generated by AI
    candidate_docs / internship_docs         Retrieved documents
    candidate_context / internship_context   Formatted text for the LLM
    web_context                              Extra context from web search
    raw_report                               The JSON string from the LLM
    resources                                Web-searched resource links
    grounding_passed                         Did the reflection check pass?
    retry_count                              How many reflection retries so far?
    analysis_report_path                     Where to save the report JSON

THE 8 NODES (in order):

  Node 1: generate_queries_node
    Asks the LLM to create 4 search queries each for the resume and the JD.
    Purpose: smarter, dynamic queries instead of hardcoded ones.
    Example output: ["Python skills and frameworks", "REST API experience",
                     "education and degree level", "project portfolio"]

  Node 2: retrieve_node
    Runs each query against the FAISS vector database.
    Uses _multi_query_retrieve() which deduplicates results by content prefix.
    Returns candidate_docs and internship_docs.

  Node 3: grade_docs_node  ← CRAG pattern
    For each retrieved document, asks the LLM: "Rate relevance 1-5".
    Keeps documents scoring 3 or above. Filters out off-topic chunks.
    This is the Corrective RAG (CRAG) pattern — cleaning retrieval results.

  Routing after Node 3:
    If total kept docs < 2 → go to web_search (Node 4)
    Otherwise → skip to generate_report (Node 5)

  Node 4: web_search_node  (optional)
    Uses DuckDuckGo to search the internet for the internship's required skills.
    Runs only when the local vector database returned too few relevant docs.
    Adds web_context to the state for the report generator.

  Node 5: generate_report_node
    The main LLM call. Gets candidate_context + internship_context (+ web_context)
    and asks the LLM to return a full JSON report with:
    matched_skills, missing_skills, readiness_score, learning_plan,
    resources, timeline_weeks, recommended_projects.

  Node 6: generate_resources_node
    Searches DuckDuckGo for real free learning resources for each missing skill.
    Asks the LLM to extract clean resource entries from search results.
    This replaces hallucinated URLs with verified ones.

  Node 7: reflect_node  ← Self-RAG pattern
    Asks the LLM to audit its own report against the candidate evidence.
    "Is every matched skill actually supported by the resume text?"
    Returns grounding_passed: true/false.

  Routing after Node 7:
    grounding_passed=false AND retry_count < 2 → loop back to Node 2
    Otherwise → go to save_report (Node 8)

  Node 8: save_report_node
    Parses the raw JSON report into a SkillGapReport dataclass.
    Merges the web-sourced resources into it.
    Saves the final report to a JSON file at analysis_report_path.
    Returns the full state so app.py can read the report path.

THE GRAPH STRUCTURE (as a diagram):

  generate_queries → retrieve → grade_docs ─── (≥2 docs) ──→ generate_report
                       ↑                   └── (<2 docs) ──→ web_search ─→ ↗
                       │                                                    │
                       └────────── (retry) ──── reflect ←── generate_resources
                                                   │
                                             (passed or max retries)
                                                   ↓
                                               save_report → END


--------------------------------------------------------------------------------
FILE 5: pipeline.py  (connects UI to graph)
--------------------------------------------------------------------------------

run_agentic_analysis(file_bytes, filename, jd_text)

  This function is the bridge between the Streamlit button click and
  the full LangGraph pipeline.

  STEP BY STEP:
    1. Creates a unique session_id (8-char hex UUID)
    2. Creates workspace paths: workspaces/session_XX_candidate/
                                workspaces/session_XX_internship/
    3. Writes the uploaded resume bytes to a temp file
    4. Ingests the resume into a FAISS workspace (calls ingestion.py)
    5. Writes the JD text to a temp file
    6. Ingests the JD into a separate FAISS workspace
    7. Sets up initial AgentState with workspace IDs and empty fields
    8. Streams events from the LangGraph graph (yields each node's output)
    9. In the finally block: deletes all temp files and workspace dirs

  It is a GENERATOR function (uses yield) so app.py can show real-time
  progress as each node completes. The cleanup in the finally block always
  runs even if an error occurs mid-pipeline.


--------------------------------------------------------------------------------
FILE 6: skill_gap_analyzer.py  (the structured report class)
--------------------------------------------------------------------------------

Used by deep mode's save_report_node to parse and save the final report.

CLASS: SkillGapAnalyzer

  Also has a standalone analyze() method that does its own retrieval and
  LLM call (used when running from the command line, not through the graph).
  In the graph, only the helper methods are used:
    _parse_report(raw_json_string) → SkillGapReport dataclass
    save_report(report, path)      → writes JSON file to disk
    _build_fallback_report(...)    → deterministic regex-based fallback

DATACLASS: SkillGapReport
  Frozen dataclass (immutable) with typed fields:
  candidate_summary, internship_summary, matched_skills, missing_skills,
  learning_plan, resources, timeline_weeks, recommended_projects,
  readiness_score, raw_response.


--------------------------------------------------------------------------------
FILE 7: export.py  (downloads)
--------------------------------------------------------------------------------

Three export functions:

  generate_html_report(report, candidate_name)
    Returns a self-contained HTML file with all results formatted.
    Includes skills badges, learning plan table, resources, interview Q,
    resume tips, and projects. Users can open in browser → print → save as PDF.

  generate_resume_pdf(data)
    Takes the structured resume dictionary from generate_tailored_resume()
    and builds a clean PDF using fpdf2.

    PDF LAYOUT:
      - Name (large, centred, bold)
      - Contact line: email | phone | linkedin | github
      - Blue horizontal rule
      - Professional Summary
      - Experience (each job: title + company + date, then bulleted list)
      - Skills (rows of 6, separated by |)
      - Education (degree + institution + year)
      - Projects (name: description)

    Uses Helvetica (built-in PDF font). Strips non-Latin characters with
    _safe() since core fonts don't support Unicode symbols.
    multi_cell() is always called with explicit width (not 0) because
    fpdf2's width=0 means "full page width" not "remaining width",
    which causes rendering errors after indented cells.

  generate_json_bytes(report)
    Simple JSON serialisation of the report dict as UTF-8 bytes.

FILE 8: progress.py  (skill learning tracker)
--------------------------------------------------------------------------------

Manages the sidebar progress tracker — lets users check off skills as
they learn them, updating their effective readiness score.

  STORAGE: progress.json file on disk.
  FORMAT:  {"missing_skills": [...], "learned_skills": [...]}

  KEY FUNCTIONS:
    set_missing_skills(skills)   Called after every analysis, stores the gaps.
    toggle_skill(skill, learned) Marks a skill as learned or unlearned.

    get_all_missing()            Returns all missing skills to display.
    effective_score(base, matched, missing)
      Adjusts the base readiness score upward for each skill that was
      missing but has since been learned.

HOW THE FILES CONNECT — FULL FLOW WALKTHROUGH
--------------------------------------------------------------------------------

EXAMPLE: User uploads "resume.pdf" and pastes a Python job description,
         selects Quick mode, clicks "Analyse my fit".

  1. app.py: button clicked
     - uploaded_file.read() had already been consumed by extract_text_from_pdf()
       so app.py calls uploaded_file.seek(0) first, then reads the bytes again
     - calls get_ai_analysis(resume_text, job_description) from analyzer.py

  2. analyzer.py: get_ai_analysis()
     - Truncates resume to 3000 chars, JD to 2000 chars
     - Step 1: _get_skills_and_score() → LLM → {"matched": [...], "score": 72}
     - Step 2: _get_plan_and_resources() → LLM → week-by-week plan
     - Step 3: get_interview_questions() + get_resume_suggestions() → LLM × 2
     - Returns full report dict

  3. app.py: receives report dict
     - Saves to st.session_state._result (so tab buttons won't lose it)
     - Calls set_missing_skills() from progress.py
     - Renders score cards, Plotly charts, 9 result tabs

  4. User clicks "🤖 ATS Check" tab → clicks "Run ATS Check"
     - Streamlit reruns the script (run_btn is now False)
     - app.py reads from st.session_state._result to get resume_text + JD
     - Calls check_ats_score(resume_text, jd) from analyzer.py
     - _ats_local() runs instantly (regex, no API)
     - LLM generates 5 improvement suggestions
     - Saves to st.session_state.ats_report, renders results

  5. User clicks "✉️ Cover Letter" tab → clicks "Generate Cover Letter"
     - Same session_state pattern
     - Calls generate_cover_letter(resume_text, jd, matched) from analyzer.py
     - Returns plain text, shown in editable text area with download button

  6. User clicks "📄 Resume Builder" tab → clicks "Generate Tailored Resume"
     - Calls generate_tailored_resume(resume_text, jd, matched, missing) from analyzer.py
     - LLM returns structured JSON with rewritten bullets and tailored summary
     - app.py renders editable fields (name, summary, skills, bullets per job)
     - User edits, clicks "Download PDF"
     - Calls generate_resume_pdf(edited_data) from export.py
     - fpdf2 renders clean PDF, returned as bytes, browser downloads it


EXAMPLE: Same user selects Deep mode instead.

  1. app.py: button clicked
     - Calls run_agentic_analysis(file_bytes, filename, jd) from pipeline.py
     - Iterates over yielded events to show real-time node progress

  2. pipeline.py: run_agentic_analysis()
     - Ingests resume into workspaces/session_XX_candidate/ via ingestion.py
     - Ingests JD   into workspaces/session_XX_internship/ via ingestion.py
     - Builds initial AgentState dict
     - Calls agent_graph.stream(initial_state) — the LangGraph pipeline

  3. ingestion.py: MultiTenantIngestionPipeline.ingest()
     - Loads the PDF → LangChain Document objects
     - Splits into parent chunks (1200 chars) and child chunks (300 chars)
     - Embeds child chunks with FastEmbed (BAAI/bge-small-en-v1.5, 384-dim)
     - Stores child vectors in FAISS, parent text in LocalFileStore
     - Saves FAISS index to disk (index.faiss + index.pkl)

  4. graph.py: 8 nodes run in sequence
     - Node 1: LLM writes 4+4 search queries
     - Node 2: FAISS searches run for each query → retrieve parent docs
     - Node 3: Each doc graded 1-5 → keep only score ≥ 3
     - Node 4: (if < 2 docs passed) → DuckDuckGo web search
     - Node 5: LLM generates full report JSON from evidence
     - Node 6: DuckDuckGo searches for real resource links per skill
     - Node 7: LLM audits report for hallucinations → retry if bad
     - Node 8: skill_gap_analyzer.py parses + saves JSON report to disk
     - Each node yields its output dict back to pipeline.py → app.py

  5. app.py: reads final report from disk
     - final_state["analysis_report_path"] points to the saved JSON
     - Reads the file, loads into report dict
     - Calls interview questions + resume suggestions via analyzer.py
     - Saves to session_state, renders 9 tabs


--------------------------------------------------------------------------------
KEY CONCEPTS EXPLAINED SIMPLY
--------------------------------------------------------------------------------

GROQ API
  Groq is a cloud AI provider. You send it text, it runs a large language
  model (llama-3.3-70b-versatile) and returns text back. It has a free tier.
  The API key goes in the .env file locally, or in Streamlit Cloud secrets.
  All LLM calls in this project go through Groq.

FAISS
  Facebook AI Similarity Search. A library for fast vector search.
  Given a query, it finds the most similar stored vectors (nearest neighbours)
  in milliseconds even for millions of vectors.
  Used in deep mode to search the resume and JD content.

LANGGRAPH
  A library for building AI pipelines that can branch and loop.
  You define: nodes (functions), edges (connections between nodes),
  and conditional edges (branches based on the current state).
  The compiled graph can be streamed so you see each node's output live.

RAG (Retrieval-Augmented Generation)
  Instead of feeding the whole document to the LLM, you:
  1. Store the document in a vector database
  2. Search for relevant chunks when you have a query
  3. Feed only the relevant chunks to the LLM
  This saves tokens and focuses the LLM on what matters.

CRAG (Corrective RAG)
  An improvement on RAG. After retrieving documents, you grade them for
  relevance and throw away the irrelevant ones before passing them to the LLM.
  Node 3 in the graph implements CRAG.

Self-RAG / Reflection
  After the LLM generates a response, you ask it to verify its own output.
  In Node 7, the agent audits whether each matched skill is actually
  supported by the resume evidence. If not, it loops back and retries.

SESSION STATE (Streamlit-specific)
  Streamlit reruns the entire Python script on every user interaction
  (button click, tab switch, checkbox toggle). Variables defined in one
  run are gone in the next. st.session_state is a dictionary that
  persists across reruns, like a per-user server-side store.
  AlignAgent saves the analysis result to st.session_state._result so
  that clicking "Run ATS Check" or "Generate Cover Letter" doesn't lose
  the resume text and report.

FPDF2
  A Python library for generating PDFs from scratch.
  You set fonts, draw text with cell() and multi_cell(), draw lines,
  and call pdf.output() to get the PDF as bytes.
  The Resume Builder uses fpdf2 to create the downloadable PDF resume.

FASTEMBED
  A lightweight embedding library that uses ONNX (a model format) instead
  of PyTorch. Much smaller to install. Downloads the model file on first use.
  Converts text to 384-dimensional vectors used for FAISS searches.


--------------------------------------------------------------------------------
WHAT HAPPENS TO UPLOADED FILES?
--------------------------------------------------------------------------------

On Streamlit Cloud:

  1. Your PDF is uploaded to Streamlit's servers as bytes in memory.
     It is never written to a permanent disk location.

  2. In quick mode: the PDF bytes are read once via PyPDF to extract text.
     The text is passed to the Groq API as part of the prompt.
     No file is saved anywhere.

  3. In deep mode: the bytes are written to a temp file (tempfile.NamedTemporaryFile)
     with a random name, ingested into a FAISS workspace, then:
     - The temp file is deleted immediately after ingestion
     - The FAISS workspace (workspaces/session_XX_candidate/) is deleted
       in the finally block after the graph finishes
     Nothing persists after the analysis completes.

  4. The Groq API receives text, not the PDF itself.
     The text is sent over HTTPS and subject to Groq's privacy policy.

  5. The only thing saved between Streamlit reruns is in st.session_state
     (in-memory, not on disk, gone when the browser tab is closed).

DEPLOYMENT
--------------------------------------------------------------------------------

The app is deployed on Streamlit Cloud:
  URL: https://alignagent-yboyjjcrws3vkuc3yujiub.streamlit.app

STREAMLIT CLOUD SETUP:
  - Code: pushed to GitHub at github.com/Lakhan-Singh123/AlignAgent
  - Secrets: GROQ_API_KEY set in the Streamlit Cloud dashboard (Settings → Secrets)
  - Dependencies: installed from requirements.txt using uv (fast pip)
  - System packages: packages.txt installs libopenblas-dev and libgomp1 (for FAISS)

KEY DEPLOYMENT DECISIONS:
  - environment.yml was deleted — it was a leftover from the original Google
    Gemini version and was causing Streamlit Cloud to use conda instead of pip,
    which made langchain-groq unavailable
  - sentence-transformers was replaced with fastembed to avoid pulling in
    full PyTorch + torchvision stack (~2GB) just for text embeddings
  - faiss-cpu is unpinned (no version number) to let uv pick a compatible wheel
    for Python 3.11 (pinning to 1.7.4 had no Python 3.11 wheel)
  - plotly import is wrapped in try/except with _PLOTLY_OK flag so the app
    still runs if plotly fails to load

================================================================================
PROJECT HISTORY — HOW THIS APP EVOLVED
================================================================================

This section tells the honest story of how AlignAgent was built — the starting
point, every major change, and why each decision was made.

--------------------------------------------------------------------------------
PHASE 1 — THE GOOGLE GEMINI VERSION (where it all started)
--------------------------------------------------------------------------------

The project originally used Google Gemini as the LLM provider and ran entirely
locally on your machine.

  LLM:         Google Gemini API (gemini-pro)
  Embeddings:  nomic-embed-text (via Ollama, a local model runner)
  UI:          Basic Streamlit, single tab, minimal styling
  Features:    Just the skill gap score + a basic learning plan
  Config:      environment.yml (Conda) + .env with GOOGLE_API_KEY

HOW IT WORKED THEN:
  You had to run Ollama locally first (a separate program that serves local AI
  models). The embeddings (converting text to vectors) happened locally via
  nomic-embed-text pulled through Ollama. Gemini handled the LLM calls for
  analysis. The entire pipeline was tightly coupled to your local machine.

THE PROBLEM WITH THIS SETUP:
  1. Anyone wanting to use it needed to install Ollama, pull the model,
     keep it running, AND have a Google Gemini API key.
  2. Deploying to Streamlit Cloud was impossible because Streamlit Cloud
     can't run Ollama.
  3. environment.yml (Conda format) and requirements.txt both existed,
     causing Streamlit Cloud to get confused about which to use.


--------------------------------------------------------------------------------
PHASE 2 — SWITCHING TO GROQ + LANGGRAPH (the big rebuild)
--------------------------------------------------------------------------------

The decision was made to:
  1. Replace Google Gemini with Groq (faster, free tier, easier API)
  2. Replace Ollama/nomic-embed-text with FastEmbed (runs anywhere, no server)
  3. Build a proper agentic pipeline using LangGraph instead of one LLM call
  4. Make the app deployable to Streamlit Cloud

WHY GROQ?
  - Free tier is generous (enough for testing and demos)
  - llama-3.3-70b-versatile is a strong open-source model
  - Fast inference (~100 tokens/second vs Gemini's variable rate)
  - Simple API compatible with LangChain's ChatGroq wrapper

WHY FASTEMBED INSTEAD OF SENTENCE-TRANSFORMERS?
  sentence-transformers pulls in the full PyTorch + torchvision stack (~2GB).
  On Streamlit Cloud's free tier this causes timeouts during installation and
  often fails entirely. FastEmbed uses ONNX (a lightweight inference format)
  instead of PyTorch and installs in ~30 seconds. Same vector quality, a
  fraction of the installation size.

WHY LANGGRAPH?
  The original code was one big LLM call. If it produced a bad result, there
  was no way to catch it or retry. LangGraph lets you break the pipeline into
  discrete steps, add conditional branches (retry if reflection fails, web
  search if retrieval fails), and stream each node's output to the UI so the
  user can watch progress instead of staring at a spinner for 2 minutes.

WHAT WAS BUILT IN THIS PHASE:
  - graph.py (8-node pipeline)
  - ingestion.py (FAISS + FastEmbed)
  - pipeline.py (bridge)
  - skill_gap_analyzer.py (structured report)
  - Updated analyzer.py (Groq instead of Gemini)
  - Two modes: Quick (fast) and Deep (agentic)
  - Deleted environment.yml so Streamlit Cloud uses pip instead of conda


--------------------------------------------------------------------------------
PHASE 3 — ADDING FEATURES (ATS, Cover Letter, Resume Builder)
--------------------------------------------------------------------------------

After the core pipeline was stable and deployed, new features were added
one by one based on what would actually be useful to someone job hunting.

  Feature 1: Interview Prep tab
    Simple: pass matched and missing skills to the LLM, ask it for 6 questions
    that an interviewer for this exact role would likely ask.

  Feature 2: Resume Tips tab
    Pass the resume and JD to the LLM, ask for 5 specific, concrete improvements
    (not generic advice like "use bullet points" but role-specific suggestions).

  Feature 3: ATS Check tab
    The idea: many companies use ATS (Applicant Tracking Systems) that scan
    resumes for keywords before a human ever sees them. A resume can be
    well-written but fail ATS because it lacks the exact words from the JD.

    Decision: make the core scoring LOCAL (regex, no API). Instant feedback,
    no cost, no rate limit. The LLM is only used for the suggestion text.
    This means even if Groq is down or rate-limited, the ATS score still works.

  Feature 4: Cover Letter tab
    Simple LLM call. Give it the resume, JD, and matched skills. Ask it to
    write 3-4 paragraphs that are tailored (mentions specific skills and role)
    rather than generic ("I am writing to express my interest...").

  Feature 5: Resume Builder tab
    Most ambitious feature. The idea: instead of just suggesting edits, rewrite
    the actual resume content to be optimised for the specific job.

    Decision: output structured JSON (not plain text) so the UI can render
    editable fields. The user can then tweak name/email/bullets/summary before
    downloading the PDF. This avoids the user getting a PDF they can't edit.

    Decision: use fpdf2 (not ReportLab, not WeasyPrint) because it is pure
    Python, has no system dependencies, and generates clean PDFs. WeasyPrint
    needs GTK/Cairo system libraries that are hard to install on Streamlit Cloud.

  Feature 6: Mobile responsive layout
    Added CSS breakpoints so the app works on small screens. The Streamlit
    sidebar toggle button was nearly invisible on the dark background — added
    a glowing blue border so users know it exists on mobile.

  Feature 7: Compare Jobs tab
    Useful for job seekers with multiple offers or opportunities. Runs quick
    analysis on up to 3 JDs, shows scores side by side, highlights the best fit.


--------------------------------------------------------------------------------
PHASE 4 — DEPLOYMENT FIXES
--------------------------------------------------------------------------------

Getting the app to actually run on Streamlit Cloud took several rounds of fixes.

  Problem: conda vs pip conflict
    environment.yml existed alongside requirements.txt.
    Streamlit Cloud would detect environment.yml and try to use conda,
    which failed because langchain-groq is not on conda-forge.
    Fix: deleted environment.yml completely.

  Problem: faiss-cpu version pin
    requirements.txt had faiss-cpu==1.7.4.
    That version has no pre-built wheel for Python 3.11 on Linux.
    Streamlit Cloud uses Python 3.11. pip fell back to building from source,
    which requires a C++ compiler and takes 20+ minutes (and then fails).
    Fix: removed the version pin so pip/uv picks the latest available wheel.

  Problem: missing system libraries for FAISS
    FAISS internally uses OpenBLAS (math library) and OpenMP (parallel computing).
    They are not pre-installed on Streamlit Cloud's base image.
    Fix: added packages.txt with libopenblas-dev and libgomp1.
    (packages.txt is Streamlit Cloud's way to install apt packages.)

  Problem: sentence-transformers installation timeout
    sentence-transformers pulls in PyTorch, which is ~800MB on Linux.
    Streamlit Cloud's build times out before it finishes downloading.
    Fix: replaced sentence-transformers with fastembed everywhere.

  Problem: Groq API key not available in deployed app
    Locally, the key is in .env (loaded by python-dotenv).
    On Streamlit Cloud, .env files are not deployed (they should never be
    committed to git — API keys in git are a security incident).
    Fix: added the key as a secret in Streamlit Cloud dashboard.
    The app reads it with: os.getenv("GROQ_API_KEY") which works for both
    local .env and Streamlit Cloud secrets.

  Problem: plotly not available in some environments
    The Gantt chart uses plotly. If plotly is not installed (or fails to
    import), the whole app crashes on startup.
    Fix: wrapped plotly import in try/except and set _PLOTLY_OK = True/False.
    If False, the Gantt chart tab shows a plain text table instead.


================================================================================
BUGS WE HIT AND HOW WE FIXED THEM
================================================================================

These are the real bugs encountered during development, explained in full detail
so you understand both what went wrong and why the fix works.

--------------------------------------------------------------------------------
BUG 1 — Deep mode always returned score 0  (file stream exhaustion)
--------------------------------------------------------------------------------

SYMPTOM:
  Quick mode worked fine (score ~65–80%). Deep mode always returned 0%.
  The deep mode report showed matched_skills: [] and missing_skills: [].
  It looked like the pipeline was running but producing empty results.

ROOT CAUSE:
  Here is the exact sequence of events:

    1. User uploads resume.pdf
    2. app.py calls extract_text_from_pdf(uploaded_file)
       This function opens the PDF using PyPDF's PdfReader(uploaded_file)
       and reads ALL pages from start to finish.
       After this call, the file stream's internal position pointer is at
       the END of the file (position = last byte).

    3. For deep mode, pipeline.py needs the raw bytes of the PDF to write
       it to a temp file for ingestion.
       app.py was doing: file_bytes = uploaded_file.read()
       But because step 2 already read to the end, uploaded_file.read()
       now returns b"" (empty bytes — there is nothing left to read).

    4. pipeline.py writes empty bytes to the temp file.
    5. ingestion.py tries to load an empty PDF → gets one empty Document.
    6. FAISS ingests an empty document → retrieval returns nothing.
    7. The LLM gets no candidate evidence → returns score 0 with no skills.

  The bug was completely silent. No error was raised at any step.
  Each step got what looked like valid (but empty/trivial) input.

FIX:
  Before reading the bytes for deep mode, reset the file position:
    uploaded_file.seek(0)
    file_bytes = uploaded_file.read()

  seek(0) moves the read cursor back to the beginning of the file stream.
  uploaded_file.read() now returns all the bytes correctly.

WHY THIS IS A SUBTLE BUG:
  Python file objects are stateful streams. Reading them moves a cursor.
  Reading twice without seeking returns empty bytes the second time — no
  error, no warning. This bites many developers who are used to reading
  files by path (open("file.pdf", "rb").read() always starts from 0).
  Uploaded files in Streamlit are BytesIO objects with the same cursor
  behaviour as regular file objects.

LESSON:
  Whenever a function accepts a file object and reads it, assume the cursor
  is at the end after that call. Always seek(0) before re-reading.


--------------------------------------------------------------------------------
BUG 2 — ATS/Cover Letter buttons refreshed with no visible effect
--------------------------------------------------------------------------------

SYMPTOM:
  After running an analysis and seeing the results, clicking "Run ATS Check"
  or "Generate Cover Letter" would refresh the page but show nothing.
  The results tabs would appear completely empty.

ROOT CAUSE:
  This is a fundamental Streamlit behaviour that caught us off guard.

  Streamlit reruns the ENTIRE Python script from top to bottom on every
  single user interaction — every button click, every tab switch, every
  checkbox toggle.

  The original code structure was:
    run_btn = st.button("Analyse my fit")
    if run_btn:
        report = get_ai_analysis(...)
        resume_text = extract_text_from_pdf(...)
        # ... render all 9 tabs here, inside this if block

  When you clicked "Analyse my fit", run_btn=True, so the analysis ran
  and everything rendered. The report, resume_text, matched_skills, etc.
  were all local variables inside the if block.

  When you then clicked "Run ATS Check" (a different button):
    - Streamlit reruns the script
    - run_btn = st.button("Analyse my fit") → now False (you didn't click it)
    - The if run_btn: block is SKIPPED
    - report, resume_text, matched_skills — all gone
    - check_ats_score() can't run because it has no resume_text to work with
    - The tabs render empty

  Every sub-feature button (ATS, Cover Letter, Resume Builder) had the same
  problem: they all needed the resume and analysis result from the first button
  click, but that data was only available inside the if run_btn: block which
  doesn't execute on subsequent clicks.

FIX:
  Save everything to st.session_state after the analysis completes:

    if run_btn:
        report = get_ai_analysis(...)
        resume_text = extract_text_from_pdf(...)
        st.session_state._result = {
            "report":          report,
            "resume_text":     resume_text,
            "job_description": job_description,
            "filename":        uploaded_file.name,
        }
        st.session_state.ats_report   = None
        st.session_state.cover_letter = ""

  Then move ALL the rendering code OUTSIDE the if run_btn: block:

    _r = st.session_state.get("_result")
    if _r:
        report          = _r["report"]
        resume_text     = _r["resume_text"]
        job_description = _r["job_description"]
        # render all 9 tabs here

  Now on every rerun (whether from "Run ATS Check" or any other button):
    - _r is read from session_state (persists across reruns)
    - resume_text, report, etc. are all available
    - The ATS check button, cover letter button, resume builder button
      all work correctly because they can read the data they need

WHY THE KEY IS "_result" (with underscore):
  Streamlit reserves some session_state keys for internal use.
  Using a leading underscore is a convention to mark it as "internal to
  this app" and avoid collisions with Streamlit's own keys.

LESSON:
  In Streamlit, treat every button click as a fresh page load.
  Any data that needs to survive across multiple button clicks must be
  stored in st.session_state before the first button's handler exits.


--------------------------------------------------------------------------------
BUG 3 — fpdf2 FPDFException: Not enough horizontal space
--------------------------------------------------------------------------------

SYMPTOM:
  Clicking "Download Resume PDF" crashed with:
    FPDFException: Not enough horizontal space to output text chunk
    in multi_cell()

  The crash happened specifically when rendering bullet points under
  an experience entry.

ROOT CAUSE:
  The original bullet rendering code was:
    pdf.set_x(pdf.l_margin + 5)  # move cursor 5mm right for indent
    pdf.cell(5, 5, "-")          # draw the dash bullet
    pdf.multi_cell(0, 5, clean)  # write the bullet text

  The mistake is in multi_cell(0, ...).

  In fpdf2, multi_cell(width=0, ...) means: use the full page width
  starting from the LEFT MARGIN, NOT from the current cursor x position.

  So here is what was actually happening:
    - Page width: 210mm (A4)
    - Left margin: 16mm, Right margin: 16mm
    - Available width: 210 - 16 - 16 = 178mm
    - pdf.set_x(pdf.l_margin + 5) moves cursor to x=21mm
    - pdf.cell(5, 5, "-") draws the dash, cursor moves to x=26mm
    - pdf.multi_cell(0, 5, clean) tries to write text starting from
      x=26 but with width=178mm (the full page width from left margin)
    - 26 + 178 = 204mm — that's past the right margin (194mm)
    - fpdf2 raises: "Not enough horizontal space"

FIX:
  Never use multi_cell with width=0 after moving the cursor.
  Always pass an explicit width that accounts for the current x position:

    indent = 5
    bw = pdf.w - pdf.l_margin - pdf.r_margin - indent  # 178 - 5 = 173mm
    pdf.set_x(pdf.l_margin + indent)   # cursor at x=21mm
    pdf.multi_cell(bw, 5, f"- {clean}")  # writes 173mm wide → fits in 194mm

  By combining the dash into the text string (f"- {clean}") and using
  one multi_cell call instead of cell + multi_cell, we also avoid the
  cursor position issue entirely.

LESSON:
  In fpdf2, multi_cell width=0 is NOT "use remaining space". It is
  "use full available width from left margin". Always compute and pass
  the explicit width when you have indented content.


--------------------------------------------------------------------------------
BUG 4 — environment.yml caused Streamlit Cloud to use conda (deploy failure)
--------------------------------------------------------------------------------

SYMPTOM:
  Streamlit Cloud build failed with errors about packages not found.
  Specifically: langchain-groq, fastembed, and other packages were
  listed as "not available" even though they were in requirements.txt.

ROOT CAUSE:
  The project had BOTH environment.yml AND requirements.txt.
  environment.yml was a leftover from the original Google Gemini version
  (Conda was used to manage that environment locally).

  Streamlit Cloud's build system detects which package manager to use
  by looking at which config files are present:
    - requirements.txt present → use pip
    - environment.yml present → use conda
    - BOTH present → conda takes priority

  When conda was used, it tried to install packages from conda-forge.
  langchain-groq, fastembed, and several other packages are not on
  conda-forge (they are pip-only packages). The build failed.

FIX:
  Deleted environment.yml from the project.
  With only requirements.txt present, Streamlit Cloud uses pip correctly
  and all packages install successfully.

LESSON:
  On Streamlit Cloud, if you have an environment.yml in your repo from
  a previous local conda setup, delete it before deploying. It will
  silently override your requirements.txt.


--------------------------------------------------------------------------------
BUG 5 — faiss-cpu version pin had no Python 3.11 wheel
--------------------------------------------------------------------------------

SYMPTOM:
  Streamlit Cloud deployment ran for 20+ minutes and then failed.
  The build log showed pip trying to compile faiss-cpu from source,
  downloading a C++ toolchain, and eventually timing out.

ROOT CAUSE:
  requirements.txt had: faiss-cpu==1.7.4

  Pre-built Python wheels (binary packages) are compiled for specific
  Python versions and operating systems. faiss-cpu 1.7.4 only had wheels
  for Python 3.8, 3.9, and 3.10. It had NO pre-built wheel for Python 3.11.

  When pip can't find a pre-built wheel, it falls back to building the
  package from source code — which requires a C++ compiler, cmake, BLAS
  libraries, etc. On Streamlit Cloud this takes very long and usually
  times out (or fails because not all tools are present).

FIX:
  Remove the version pin. Change faiss-cpu==1.7.4 to just faiss-cpu.
  pip then picks the latest version which has proper Python 3.11 wheels.

LESSON:
  Be careful pinning versions of packages that have pre-built binary wheels.
  If you pin to a version that predates Python 3.11 wheels, deployment fails
  silently (it attempts source compilation instead of erroring immediately).
  Only pin versions when you have a specific compatibility reason to do so.


--------------------------------------------------------------------------------
BUG 6 — sentence-transformers caused installation timeout
--------------------------------------------------------------------------------

SYMPTOM:
  Streamlit Cloud build got stuck at "Installing sentence-transformers"
  for 8–10 minutes, then either timed out or succeeded but left no memory
  for the app itself to start.

ROOT CAUSE:
  sentence-transformers depends on:
    - torch (PyTorch) — ~800MB on Linux
    - torchvision — ~200MB
    - transformers — ~400MB
  Total download: ~1.4GB just for text embeddings.
  Streamlit Cloud's free tier has limited build time and memory.

  Even when it didn't timeout, having PyTorch loaded in memory meant the
  Streamlit app itself sometimes ran out of RAM when running the analysis.

FIX:
  Replaced sentence-transformers with fastembed in requirements.txt
  and updated ingestion.py to use FastEmbedEmbeddings instead of
  HuggingFaceEmbeddings.

  fastembed uses ONNX Runtime instead of PyTorch.
  Total installation size: ~80MB (20x smaller).
  Model file (BAAI/bge-small-en-v1.5): ~25MB, downloaded on first use.
  Same 384-dimensional vector quality for semantic search purposes.

LESSON:
  For text embeddings in a deployed web app, choose a library that does
  not pull in the full ML training stack. You only need INFERENCE (running
  the model), not training capabilities. ONNX-based libraries like
  fastembed give you inference at a fraction of the weight.

BUG 7 — Sidebar toggle invisible on mobile
--------------------------------------------------------------------------------

SYMPTOM:
  On mobile, the app opened with no visible way to access the sidebar
  (Skill Progress Tracker). The sidebar toggle button existed but was
  nearly invisible — dark arrow icon on a dark background.

ROOT CAUSE:
  Streamlit's default sidebar toggle button ([data-testid="collapsedControl"])
  uses a subdued color that blends into the dark theme.
  On desktop, users can hover and see it. On mobile, hover doesn't exist,
  and the button is so faint that users simply don't see it.

FIX:
  Added CSS targeting the exact Streamlit test ID:

    [data-testid="collapsedControl"] {
        border: 2px solid #2563EB !important;
        border-radius: 8px !important;
        box-shadow: 0 0 8px rgba(37, 99, 235, 0.5) !important;
    }

  This adds a glowing blue border around the toggle button so it stands
  out on any background, especially on mobile.

WHY USE data-testid?
  Streamlit's internal HTML structure uses data-testid attributes to
  identify UI elements. These are semi-stable (Streamlit doesn't change
  them often) and more reliable than CSS class names (which are minified
  hash strings like ".stSidebar-2ab3c4").

LESSON:
  Always test your Streamlit app on a small screen before calling it done.
  Dark-theme apps especially need care — elements that are visible at full
  opacity on desktop become invisible when alpha-blended onto dark backgrounds.


================================================================================
DESIGN DECISIONS — WHY WE BUILT IT THIS WAY
================================================================================

These are the conscious trade-offs and architectural choices, explained with
the reasoning behind each one.

--------------------------------------------------------------------------------
DECISION 1 — Two modes instead of one
--------------------------------------------------------------------------------

WHY NOT JUST ONE MODE?
  We could have had a single pipeline (always use LangGraph with FAISS).
  But that takes 2-3 minutes every time. For someone who just wants a quick
  check of whether a job is worth applying for, 2-3 minutes feels like forever.

WHY NOT JUST QUICK MODE?
  Quick mode sends the full resume text (up to 3000 chars) to the LLM in one
  prompt. This means the LLM has to do extraction, comparison, and report
  generation all in one shot. Deep mode uses retrieved evidence to ground each
  claim — it's more accurate for longer, more complex resumes.

THE TRADE-OFF:
  Quick mode: faster, slightly less accurate, good for initial screening.
  Deep mode: slower, more accurate, better for important applications.

  Having both lets the user choose based on how much time they want to spend.


--------------------------------------------------------------------------------
DECISION 2 — ATS scoring uses local regex (not LLM) for the score
--------------------------------------------------------------------------------

WHY NOT JUST ASK THE LLM FOR AN ATS SCORE?
  You could. But:
    1. Every check would cost an API call (~5 seconds wait)
    2. The LLM's score would not be explainable — you couldn't tell the user
       exactly which keywords were missing or which sections were absent
    3. If Groq is rate-limited or down, ATS checking would break entirely

  Regex-based local checks are:
    - Instant (milliseconds)
    - Always available (no network dependency)
    - Fully explainable (can show exactly what was found/missing)
    - Free (no API tokens consumed)

  The LLM is still used for the SUGGESTIONS (the "how to fix it" part)
  because that requires understanding and creativity, not just pattern matching.

THE FORMULA:
  ats_score = keyword_score × 0.40 + section_score × 0.35 + verb_score × 0.25

  Keyword match gets the highest weight (40%) because ATS bots primarily
  scan for exact-match keywords from the job description.
  Section presence (35%) — most ATS systems reject resumes with missing
  standard sections (no "Skills" section = no skills match possible).
  Action verbs (25%) — indicators of well-written, achievement-focused bullets.


--------------------------------------------------------------------------------
DECISION 3 — Resume Builder outputs JSON, not a pre-made PDF
--------------------------------------------------------------------------------

WHY NOT JUST RETURN A PDF DIRECTLY?
  If the LLM rewrites your resume and immediately generates a PDF, you have no
  way to review or edit it. The LLM might get your job title slightly wrong,
  or rewrite a bullet in a way you don't like.

  By returning JSON first and rendering editable fields, the user can:
    1. Review every piece of content before it becomes a PDF
    2. Edit the summary, skills, or any bullet to their preference
    3. Then download the PDF from the edited version

  The PDF is generated from whatever the user edits, not directly from the LLM.

WHY FPDF2 FOR THE PDF?
  Three candidates were considered: fpdf2, ReportLab, WeasyPrint.
    - ReportLab: good quality but complex API, and the open-source version
      has restrictions on commercial use.
    - WeasyPrint: converts HTML to PDF (great looking output) but requires
      GTK, Pango, and Cairo system libraries. These are hard to install on
      Streamlit Cloud without complex packages.txt entries.
    - fpdf2: pure Python, zero system dependencies, simple API, already
      familiar from the existing export.py HTML report code.
  fpdf2 was the clear choice for a deployed web app.


--------------------------------------------------------------------------------
DECISION 4 — Session state key is "_result", not "result"
--------------------------------------------------------------------------------

The leading underscore is intentional. Streamlit has its own internal session
state keys. While Streamlit doesn't currently use "result", using "_result"
follows the Python convention of underscore-prefix for "internal/private" and
makes it obvious this key is managed by the app code, not by the framework.

It also avoids accidental conflicts if Streamlit adds a "result" key in a
future version.


--------------------------------------------------------------------------------
DECISION 5 — Groq API key NEVER in source code
--------------------------------------------------------------------------------

This is not negotiable. API keys in source code = security incident.

If a key is committed to a public GitHub repo, it can be scraped by bots
within minutes. The key gets revoked, your account may be suspended, and
any usage charges are your responsibility.

The key lives in two places only:
  - Locally: .env file (listed in .gitignore so it is never committed)
  - Deployed: Streamlit Cloud dashboard → Settings → Secrets

The app reads it with os.getenv("GROQ_API_KEY"). If the env var is not set,
the app shows a clear error message instead of crashing silently.


--------------------------------------------------------------------------------
DECISION 6 — DuckDuckGo for web search (not Google/Bing)
--------------------------------------------------------------------------------

Node 4 (web_search_node) and Node 6 (generate_resources_node) use DuckDuckGo
via the duckduckgo_search Python library.

WHY NOT GOOGLE?
  Google Search API requires billing setup and credit card, even for small
  volumes. The project aims to be entirely free to run.

WHY NOT BING?
  Microsoft Azure Bing Search API requires an Azure account and has no free tier.

WHY DUCKDUCKGO?
  The duckduckgo_search library makes anonymous (no API key, no account needed)
  HTTP requests to DuckDuckGo's unofficial search endpoint. It is free,
  requires no credentials, and works well for finding tutorial and course links.
  The trade-off is it is unofficial and could change if DuckDuckGo alters
  their HTML structure — but it is stable enough for this use case.


--------------------------------------------------------------------------------
DECISION 7 — Reflection node retries max 2 times (not unlimited)
--------------------------------------------------------------------------------

The reflect_node (Node 7) checks if the generated report is well-grounded
in the candidate evidence. If not, it loops back to retrieve → grade → generate.

WHY MAX 2 RETRIES?
  Every retry runs the full retrieval and generation sequence again (~30-60s).
  After 2 retries, if the report is still not well-grounded, something
  structural is wrong (perhaps the resume or JD is very short and there just
  isn't much evidence). Retrying endlessly would make the user wait forever.

  In practice, reflection passes on the first or second attempt ~95% of the time.
  The 2-retry cap is a safety net, not a regular code path.


--------------------------------------------------------------------------------
DECISION 8 — Cover letter has a plain-text fallback
--------------------------------------------------------------------------------

Every LLM call in analyzer.py has error handling. For the cover letter,
if the Groq API is unavailable or returns an unparseable response, the code
returns a generic plain-text cover letter template that the user can edit.

This is better than crashing. A generic letter that the user can personalise
is more useful than an error message.

The same fallback principle applies to all LLM calls:
  - Analysis: _local_fallback() uses regex to extract skills from the resume
  - ATS: scoring still runs locally even if LLM suggestions fail
  - Resume Builder: returns a minimal dict with the original resume text
    chunked into sections rather than crashing
